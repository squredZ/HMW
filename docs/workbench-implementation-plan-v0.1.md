# 个人工作台实施计划

状态：以当前本地原型为起点，按单负责人、临时访客模型继续实施。本文是剩余工作计划，不代表所有目标已经实现或可以试点。需求和设计依据见 [需求与设计基线](workbench-requirements-design-v0.1.md)；实际启动方式和限制见 [README](../README.md)。历史任务、接口草案和测试思路保存在 [原计划归档](archive/workbench-implementation-plan-original.md)，其中多人账号和角色设计已经废弃。

## 1. 已确认的边界

- 工作台只有一位长期负责人。同事通过链接使用临时会话，不创建同事长期账号，不建设项目成员管理。
- 项目组织知识和问题；负责人明确开放的已发布知识和个人状态才对访客可见，默认不公开。源文件和派生结果不得绕过原内容的授权或撤销。
- “关于我”的内容、进度和投入只能由负责人手动维护；访客、知识导入、对话、Agent、Worker 和任务结果均无写入路径。
- Agent 运行时方向为 Pi；MVP 不安装、不运行、不依赖 EverOS。只读问答已接入 Pi，默认关闭模型；保留未来替换记忆实现的边界，不提前宣称已有 EverOS 适配能力。
- 当前账号、临时会话、SQLite 和本地存储仅供开发；一键启动绑定本机，不等于对同事开放的部署。真实部署、数据、身份及模型环境须单独验证。
- 代码遵循 [开发铁律](../AGENTS.md)，包括 Clean Code、必要注释、并发与资源管理、日志和审计。验收须说明实际覆盖范围。

## 2. 当前实现与缺口

| 能力 | 本地原型已有 | 尚未完成 |
|---|---|---|
| 身份与个人状态 | 开发账号登录、临时访客会话；负责人手动保存、发布、撤回状态及部分项目投入 | 正式负责人认证、生产会话管理、完整状态字段和投入可视化 |
| 知识导入 | Markdown/TXT、DOCX/PPTX 文件及手动文字；独立 Worker、草稿预览、人工发布；旧版 Office 给出转换提示 | 对话消息快照导入、草稿编辑、旧格式隔离转换、Office 原图对照、编码确认及重试 |
| 知识管理 | 按项目、状态、文件名浏览；下载原件、发布、访客可见性、停用 | 分类、条目关系、真正的版本演进与比较、基线、恢复、保留清理 |
| 访客检索 | 检索明确开放的已发布知识，校验来源；可选只读 Pi 生成、引用编号校验与调用后权限复核 | 更完整的答案事实验证、个人状态问答、基线、对话历史及转问题单 |
| 问题 | 访客提交标题和描述；负责人分页查看、手动标记已解决 | 完整字段、附件、状态流转、审计历史、幂等和限流、访客找回、任务关联 |
| 部署与配置 | Linux/macOS 和 Windows 的依赖安装与本地启动脚本；配置模板可显式启用 DeepSeek 兼容模型 | Windows 实机验证、团队可访问的生产部署、真实身份、备份与恢复、日志及保留策略 |

当前访客项目列表和问题提交只包含至少有一条对访客开放的已发布知识的项目；这是现有实现约束，不视为已经确认的长期产品规则。现有 `new → resolved` 也是最小原型状态，并非完整问题状态机。

## 3. 待决策的产品与运行边界

这些问题不阻塞与之无关的本地开发，但相关能力上线前必须确定并记录：

1. **项目开放：** 访客是否可以进入或向没有公开知识的项目提交问题；如可以，负责人如何显式开放项目本身。
2. **会话和找回：** 临时会话、问题和任务各自的保留期限；离开页面后是否需要找回，以及如何通过不可猜测、可撤销的凭证授权。不能把任务 ID 当作访问凭证。
3. **审批：** 访客发起与负责人发起的任务分别如何确认；何种动作必须由负责人批准、超时和配置变更如何处理。不能假设存在代理审批人或第二个长期账号。
4. **生产环境：** 负责人身份认证、同事网络入口与安全边界、模型和数据处理环境、备份及保留策略。生产配置不得复用开发身份。
5. **模型范围：** 不同供应商的 API URL、model、思考强度及能力差异；具体 API 和费用限制需按实际供应商验证。此前允许的真实 DeepSeek 凭证仅在必要验证时按用户授权使用，不写入代码或日志。

## 4. 后续工作顺序与验收

下列顺序是实施建议，可按实际使用反馈调整；每项先编写针对性失败测试，完成实现后运行相关测试，并按改动风险补充权限、并发与资源验证。只在验收条件全部满足时标记完成，不因已有局部原型而提前勾选。

### 4.1 稳固基础与问题闭环

- [ ] 为问题提交增加幂等键、限流与有界存储；网络失败重试不得重复产生记录。给访客清晰的失败及重复提交反馈。
- [ ] 设计和实现问题状态迁移、版本冲突及审计；从现有 `new`、`resolved` 安全迁移，不覆盖已有数据。目标状态参考设计基线，实际过渡规则须覆盖重开和无效迁移。
- [ ] 完善问题字段、附件预算、负责人筛选与关联知识；访客查回仅在第 3 节的访问规则确定并实现后开放。
- [ ] 测试访客越权、不同会话隔离、重复提交、并发状态变更、共享撤销、正文和凭证不进入日志；在实际目标数据库验证事务行为。

涉及：`apps/api/workbench/issues/`、`apps/api/workbench/guests.py`、`apps/web/src/GuestIssues.tsx`、`apps/web/src/OwnerIssues.tsx` 和相关测试。当前实现部分仍位于 `app.py`，重构时应保持 API 兼容并避免无关改动。

### 4.2 知识生命周期和来源

- [ ] 支持负责人编辑草稿并生成可追溯的新知识版本；已发布正文不能原地覆盖。明确停用、重新发布和来源依赖的迁移与并发冲突处理。
- [ ] 完善导入恢复和重试、错误状态、文件与文本大小边界；Office 文件按目标实现隔离转换、原件对照及修订 / 图片核对，旧格式无转换器时保持明确提示。
- [ ] 实现分类、可确认的关系、版本比较、基线和缺项视图；开放范围变化后检索、下载、关系图及基线不得泄露未开放内容。
- [ ] 实现明确的来源与产物保留 / 清理策略；有效引用不得被误清理，显式撤销或合规删除时先处理依赖。
- [ ] 测试跨项目授权、来源完整性、历史版本、并发编辑、撤权后旧引用、导入失败清理、Office 不安全输入及实际数据库锁行为。

涉及：`apps/api/workbench/knowledge/`、`apps/api/workbench/jobs/`、`apps/web/src/KnowledgeImport.tsx`、`apps/web/src/KnowledgeManager.tsx`。关系、基线和迁移模块按设计新增；历史接口名称仅供参考。

### 4.3 Pi、模型与有出处的回答

- [ ] 在现有提取式检索与生成之间建立清晰的服务端边界：仅将当前获准且可核验的证据交给 Pi / 模型；提示注入作为数据，不改变工具或权限。
- [ ] 完成 Pi 运行时和模型适配器，提供模拟实现；统一读取经过校验的服务端配置（API URL、model、凭证和供应商支持的思考强度）。当前 `.hmw.toml` 的 `[llm]` 字段仅在明确启用时生效；后续还需验证供应商能力差异与生产密钥管理。
- [ ] 设计回答与证据契约、引用定位和无依据反馈；展示及下载时复核授权，模型失败或证据不足不伪造答案。不把聊天或导入写入个人状态。
- [ ] 使用模拟服务测试正常、超时、取消、预算、格式错误、提示注入和撤权；必要的真实 DeepSeek 验证使用脱敏样例且不打印密钥或敏感请求。记录真实测试范围和费用限制。
- [ ] 个人状态问答、对话保存、基线查询及转问题单分别实现并验证；不能把当前关键词摘录称为完整问答。

涉及：`apps/api/workbench/questions/`、未来 Pi / 模型适配模块、服务端配置和 `apps/web/src/GuestQuestions.tsx`。EverOS 不作为依赖或验收前提。

### 4.4 受控后台任务和审批

- [ ] 在访客任务访问与审批规则确定后，定义任务 / 运行代次 / 工具动作 / 结果的版本化契约。先实现模拟的日志分析、问题分诊和交接准备，不开放任意 Shell、代码修改或外部写入。
- [ ] 在 API 和独立 Worker 中实现持久状态、租约、心跳、fencing、预算、重试、取消、恢复与幂等；执行前重新校验来源和授权。
- [ ] 对需要确认的动作实现负责人审批、输入与策略摘要绑定、过期、变更失效和一次性消费；负责人自发任务如何确认须遵循第 3 节最终决定。
- [ ] 结果先验证再人工验收；Agent 不能自动关闭问题、修改个人状态或扩大数据受众。测试失效租约、恢复、重复领取、审批并发、取消竞态和证据失败。

### 4.5 生产身份、部署和试点

- [ ] 明确负责人认证、访客入口、安全会话、TLS、跨进程会话与资源授权；不得以当前开发账号 / 进程内会话直接对外提供服务。
- [ ] 验证 PostgreSQL 多进程事务、Worker 故障恢复、对象存储、备份恢复、文件清理与审计保留；明确容量、限流、日志、监控及密钥管理。
- [ ] 在 Windows 实机验证 `setup.cmd`、`start.cmd`、进程树关闭及路径含空格；在目标环境验证 Linux/macOS 过程。本地启动器不是生产部署工具。
- [ ] 使用授权的脱敏样本进行端到端与安全测试，并记录问题、限制及人工判断。目标评测样本为 20 个问题、10 份日志和 10 张历史问题单；未完成时不声称达到试点门槛。

## 5. 回归与交付标准

- 负责人手工状态、访客访问边界、来源下载与撤销、上传预算、问题登记、任务授权、日志脱敏和错误反馈按改动范围回归。
- 单元测试不能代替浏览器实际体验、PostgreSQL 多进程 / 故障测试或真实部署验证；记录实际命令、结果、警告及未覆盖项。
- 依赖按后端 `uv.lock`、Pi Agent 的 `package-lock.json` 和前端 `pnpm-lock.yaml` 锁定。更改配置字段时同步示例、校验、使用文档和兼容策略，绝不提交真实凭证。
- 交付前检查 `main` 和开发分支的状态，按用户要求进行本地合并；远程推送、真实环境部署或对外开放应按明确授权执行。
